## 1. Product Vision

IntelliFleet is RGF's cold-chain logistics control platform. The frontend must feel like **Uber Freight meets a premium EV dashboard**: confident, monochrome, data-dense but never cluttered, with cinematic motion that makes fleet operations feel alive rather than like a spreadsheet.

**One-sentence brief:** *A black-and-white, cinematically-animated operations platform where a dispatcher can watch a live cold-chain fleet move across the Philippines, and where drivers, customers, and warehouse managers each get a purpose-built view of the same truth.*

**Non-negotiables:**
- Pure black/white/grayscale palette with a single restrained accent (see Section 4).
- A real, licensed/stock **video** hero (trucks, cold-chain warehouses, highways, night driving) — never an AI-generated or illustrated hero video. Treat the hero video the way Uber Freight, Flexport, or Convoy treat theirs: cinematic, desaturated, slow motion, confident.
- 3D/motion elements must be built with real WebGL/CSS technology (Three.js, Spline export, or GSAP + SVG/Canvas) — not static mockups pretending to be 3D.
- The product must read as **enterprise-grade freight tech**, not a marketing site. Motion serves comprehension (state changes, live positions, transitions) more than decoration.

## 2. Goals & Non-Goals

1. Ship a fully navigable, responsive, animated frontend covering all 5 user roles from the proposal (Dispatcher, Driver, Warehouse Manager, Customer/Client, Superadmin).

## 4. Brand & Design System

### 4.1 Design direction — CORRECTED per client reference (Uber Freight, actual)
**Client-approved reference:** RGF supplied an actual Uber Freight page screenshot as the target look. This supersedes any dark/"tech noir" direction. The final direction is:

- **Predominantly white / very light warm-gray background** (`#FAFAFA`–`#F5F5F5`), not black, not dark mode, as the default surface everywhere — public site AND internal dashboards.
- **Black or near-black text** on white — bold, large, confident headlines set in a clean grotesque sans (Uber's own type feel: think Helvetica Neue / Inter Tight, heavy weight for headlines, regular for body).
- **Real photography only** — actual trucks, drivers, warehouses, cold-chain operations, people at work. No stock "tech" imagery, no illustrations standing in for real content.
- **No decorative icons.** Navigation, industry/category tabs, and section labels are plain text links (underline or weight change on active state) — exactly like the reference: `Auto  Chemical  Construction  CPG  Food & Beverage  Manufacturing  Packaging`. Functional icons inside the operational dashboards (map markers, status glyphs) are the only exception, and even there keep them minimal and monochrome.
- **One CTA style:** solid black pill/rounded-rect button with white text ("Learn more", "Request a demo") — no gradients, no color CTA.
- **Color is used sparingly and only where it's operationally meaningful** (a status dot for "critical" vs "on time" in the ops dashboards) — the public marketing site and most of the app should read as pure black/white/gray.

### 4.2 Color tokens (corrected — light-first)

```
--paper:          #FAFAFA   /* primary page background everywhere, incl. app */
--surface:        #FFFFFF   /* cards, panels */
--surface-alt:    #F2F2F0   /* secondary section backgrounds, alternating bands */
--hairline:       #E4E4E2   /* borders, dividers */
--ink:            #0B0B0B   /* primary text, headlines — near-black not pure black */
--ink-secondary:  #55565A   /* body copy, secondary text */
--ink-muted:      #8A8B8E   /* captions, timestamps, placeholders */
--cta-black:      #0B0B0B   /* solid CTA button fill */
--cta-black-hover:#242424
--danger:         #C4291F   /* critical alerts only — operational screens only */
--success:        #1E7B44   /* delivered/on-time only — operational screens only */
```

Rule: this is a **light theme throughout** — public site, dispatcher tower, admin, client portal. There is no separate dark theme in this build. `--danger`/`--success` appear only as small status dots/chips inside operational screens (Control Tower, Alerts, Orders) — never on the marketing site, never as page backgrounds.

### 4.3 Typography

- **Display face:** `Neue Machina` or `General Sans` (fallback: `Inter Tight`) — used for hero headlines, page titles, big metrics. Set tight (-2% to -4% tracking), heavy weight (700–800).
- **Body face:** `Inter` — used for all UI copy, tables, forms. Regular/medium weights only.
- **Data/mono face:** `JetBrains Mono` or `IBM Plex Mono` — used for vehicle IDs, coordinates, timestamps, reference numbers (e.g. "A-1842", "DCD8953"), reinforcing the "operational truth" feel.

Type scale (rem, base 16px):
`Display XL 4.5 / Display L 3 / Display M 2.25 / H1 1.75 / H2 1.375 / Body 1 / Small 0.875 / Micro 0.75 (mono, uppercase, tracked +4%)`

### 4.4 Layout & spacing
- 8px base grid. Container max-width 1440px on marketing pages; full-bleed edge-to-edge on operational dashboards (map/table screens use every pixel).
- Card radius: 12px on marketing/consumer surfaces, 4px (near-sharp, "industrial") on operational dashboards — this radius contrast is intentional and reinforces "consumer vs. operator" surfaces.
- Hairline borders (`1px solid var(--hairline)`), no drop shadows, no glow effects. Emphasis comes from weight and spacing, not color — matches the flat, clean look of the reference.

### 4.5 Motion principles
- **Page load:** one orchestrated entrance per page (staggered fade+rise, 400ms, ease `cubic-bezier(.16,1,.3,1)`), not scattered per-element animation.
- **Industry/category tabs:** clicking a tab (e.g. "Auto", "Food & Beverage" — reference pattern) crossfades the image + headline + body copy panel below it, exactly like the Uber Freight reference. This is the primary interaction pattern on the homepage, reused for role tabs (Dispatcher/Driver/Customer/Warehouse).
- **Live data (ops dashboards only):** vehicle dots on the map pulse subtly and leave a short fading trail on movement — kept quiet and monochrome (dark dot on light map), not a glowing neon effect.
- **State transitions:** status chips crossfade label changes (e.g. "En Route" → "Arrived") over 200ms rather than instant swap.
- **Scroll (marketing site only):** scroll-triggered fade/rise reveals for feature sections; parallax on the dedicated home-page 3D/video background section (see 4.6).
- **Respect `prefers-reduced-motion`:** all continuous animation (pulses, trails, parallax, tab crossfades) must fall back to static/instant states.
- **Photography, not stock-tech imagery:** every hero and section image must be real, specific, on-brand photography — actual trucks, drivers, cold-chain warehouses, RGF-relevant industries — desaturation is optional but images should read as authentic documentary photography, matching the reference exactly (natural light, real work environments, no CGI look).

### 4.6 Dedicated 3D/video home-page section
Per the corrected brief: the homepage gets **one dedicated full-width section** (not the whole page) that explains the platform's features using a **3D and/or video background** — this is the one "wow" moment, everything else on the page is calm white/black editorial layout like the reference.
- Placement: directly below the hero (which itself is a plain white/black headline + real photo, matching the reference — no video in the very first fold).
- Content: a looping real video (cold-chain trucks, warehouse, live dispatch) OR a subtle 3D visualization (e.g. a rotating low-poly Philippines map with route lines connecting warehouse → delivery nodes), rendered in **grayscale/duotone (black, white, one gray)** so it stays consistent with the rest of the page rather than looking like a separate dark-mode intrusion.
- As the user scrolls through this section, feature callouts (Live tracking / Route optimization / Cold-chain alerts / Connected channels) reveal one at a time, each with a short black headline and one line of body copy on a translucent white card over the video/3D, keeping text fully legible per accessibility requirements.
- Built with **React Three Fiber** (3D option) or a compressed real-video loop with `object-fit: cover` (video option) — background must never use a neon/dark theme; treat it as a monochrome documentary layer, not a sci-fi dashboard layer.

### 6.8 Operations Control Tower (`/app/tower`) — FLAGSHIP SCREEN
This is the single most important screen in the build. Layout: full-bleed light map (60–70% of viewport) + right-hand docked panel (30–40%) + top command bar, all on the same white/off-white background as the rest of the product — no dark dashboard theme.

**Top command bar:** RGF logo mark, global search (order/vehicle/driver/route), live clock, alert bell (badge count), user menu.

**Map (center/left, dominant):**
- Light/muted styled map (Mapbox GL or MapLibre "light" style, or a custom SVG PH map with light-gray landmass on white if no mapping license is available) showing live vehicle markers (mocked movement — see 12.2).
- Each vehicle marker = a solid black dot + heading indicator + short fading gray trail — monochrome, no glow. Only alert-state markers use `--danger` (red) or `--success` (green), and only as small status dots, never as large fills.
- Clicking a vehicle opens a slide-up mini card: driver name, vehicle ID (mono font), speed, fuel, ignition state, current route, ETA.
- Geofence zones rendered as soft dashed polygons.
- Map toggles: Live / Routes / Alerts / Heatmap (heatmap can be a stub for this phase).

**Right panel (tabbed):**
- **Fleet tab:** scrollable vehicle list, each row = status dot, vehicle ID, driver, speed, last-updated timestamp, mini sparkline of recent speed.
- **Alerts tab:** live-updating list of alert types from proposal Section 3.1 (temperature, inventory, overdue, idling, geofence, route deviation, ETA drift) — each with severity color, timestamp, "Acknowledge / Escalate / Resolve" actions.
- **Comms tab:** communication timeline per Figure 1 of the proposal — event → policy check → template → channel → provider → delivery status, rendered as a vertical timeline with channel icons (WhatsApp/Viber/SMS/Voice/Web) and status badges (Sent/Delivered/Failed/Acknowledged/Escalated).

**Bottom strip (optional, collapsible):** KPI row — active vehicles, on-time %, open alerts, avg response time — each a small animated counter (count-up on load).

**Empty/loading states:** skeleton map + skeleton list rows with shimmer, never a blank screen.

**Motion:** marker pulse is subtle and continuous; panel tab switches crossfade; new alert arrival slides in from top with a brief `--danger` or `--success` flash (matched to severity) on the row, then settles to a plain hairline card.

## 8. Tech Stack Recommendation

Match the existing IntelliFleet frontend stack referenced in the proposal (React/Vite) so this build can later merge into the real repo (`rgf-web/frontendmain/`) with minimal friction.

- **Charts:** Recharts (kept strictly black/gray/white with severity color as the only exception)
- **Forms:** React Hook Form + Zod validation
- **Icons:** Lucide React
- **Testing:** Vitest + React Testing Library for components; Playwright for critical-path e2e (login → tower → alert acknowledge, driver flow, portal tracking)

## 9. Responsive & Accessibility Requirements

- Breakpoints: 375 / 768 / 1024 / 1440 / 1920.
- Driver screens: mobile-first, designed at 375–430px first, then scaled up.
- Dispatcher/Admin screens: desktop-first (1440+), but must degrade gracefully to 1024 (tablet ops use) — not required to be usable at 375.
- Client Portal: mobile-first, since customers primarily open tracking links on phones.
- WCAG 2.1 AA: color contrast checked against the light palette (verify `--ink-secondary` and `--ink-muted` on `--paper`/`--surface` meet 4.5:1 for body text; use `--ink` where they don't), visible focus rings (2px black outline offset), full keyboard navigation, `aria-live` regions for live alert/status updates, `prefers-reduced-motion` fallback for all continuous motion.

## 10. Performance Budget

- Landing page hero video: compressed, adaptive-bitrate or at minimum a ≤6MB optimized MP4/WebM with poster image; lazy-load below-the-fold sections.
- Control Tower initial load: skeleton in <300ms, interactive map in <2s on a mid-tier laptop.
- 3D hero: must not block main-thread hero text render — mount Three.js canvas after critical text paints.
- Lighthouse targets: Performance ≥85, Accessibility ≥95, Best Practices ≥95 on the public landing page.

## 12. Mock Data Layer (so backend can plug in later)

### 12.1 Principle
Every screen fetches through a single `services/api/*.ts` abstraction using the entity shapes below (directly mapped from proposal Section 8.2 and 9.2). Swapping mock fetchers for real HTTP calls to the future backend should require no component changes.

### 12.2 Core mock entities (TypeScript interfaces to implement)
```

Route { id, name, stops[], mode: 'fastest'|'cheapest'|'shortest'|'multimodal', distanceKm, durationMin, cost }
Order { id, customerId, routeId, vehicleId, status, etaWindow, createdAt, events[] }
Alert { id, type, severity, vehicleId, orderId, message, status, createdAt, resolvedAt }
Conversation { id, subjectType, subjectId, channel, messages[] }
Message { id, conversationId, direction, channel, templateId, content, status, timestamps }
NotificationTemplate { id, name, channel, language, body, variables[], status }
User { id, name, role, email, permissions[] }
AuditEvent { id, actorId, action, target, timestamp }
```
### 12.3 Live simulation
Build a small mock "vehicle mover" utility that ticks every 2–3 seconds and nudges each mocked vehicle's lat/lng along a predefined polyline, so the Control Tower map always feels alive during demos — this is the single most important illusion for stakeholder buy-in.

### 12.4 Fixtures
Seed at least: 12 vehicles, 8 drivers, 15 orders across all status states, 10 alerts across all types/severities, 20 messages across all 5 channels and all status states, 6 templates, 5 users (one per role).

## 14. Acceptance Criteria (Frontend Phase)

1. Every route in Section 5 renders with real (mocked) data, no dead links, no lorem ipsum in production copy.
2. Control Tower shows continuously moving vehicles with pulse/trail animation and live-feeling alert arrivals.
3. Hero uses a real video asset (not AI-generated), correctly overlaid and legible.

5. Role switcher allows a reviewer to preview all 5 role experiences without a real backend.
6. All interactive elements have visible focus states and pass a basic keyboard-navigation walkthrough.
7. `prefers-reduced-motion` correctly disables continuous animation.
8. Design tokens are centralized (Tailwind config / CSS variables) — no hard-coded hex values scattered in components.
9. Mock API layer is isolated behind a single service interface per entity, ready for backend swap.
10. Lighthouse scores meet Section 10 targets on the landing page.
