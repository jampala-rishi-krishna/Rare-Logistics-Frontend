## Reuse and access model

- Live orders: `live_sales_order_cache.cached_rows_overlapping`, `cached_assigned_records`, `cached_detail`, `get_assignment` (memory-only readers); include reference TOs from existing caches when available. Never call `get_window` or `get_detail` loaders from Tracker.
- Historical rows: reuse `day_model.rows_in_range` and `trip_state.load` only for strictly past date windows. Cache bounded results, single-flight, no automatic polling. Follow-up model inspection confirmed `sales_orders.salesperson_name` **is persisted**; historical ownership uses this field with the same fail-closed exact-name rule. Historical line items come from `sales_order_lines` in one date-scoped batch.
- Current trip facts: publish small projections from the existing `trip_state.load` read and existing issue reads. Tracker itself must not warm those facts from Neon today. Missing, expired, or generation-stale facts are marked unavailable. This favors privacy and database discipline over pretending complete coverage after restart.
- Driver/helper phone numbers and raw provider payloads never enter Tracker responses or AI tools. Location requires scoped order ownership, current day, current assignment, active trip and unfinished stop. Media authorization must confirm the photo belongs to a scoped order, including when requested directly.
- Roles: Admin / Planner (alias Dispatcher) / Sales / Wet Market. Crew, warehouse and officer roles excluded. Existing `workspace_access` currently permits Sales/Wet Market only order reads and access workflow; extend explicitly for Tracker reads, Ask and feedback, plus scoped media GET.
- SO cache has `salesperson_name`; login has `full_name` / email, no trusted Zoho salesperson-id binding or channel ownership join. Safe initial scope: exact normalized salesperson-name = full-name; Wet Market additionally requires WM type/WM-SO number. Missing owner, shared department accounts, ambiguous duplicate staff names, TO without salesperson: deny for Sales/Wet Market. Do not grant an all-orders fallback. Admin/Planner can see operations records. Proposed durable verified user-to-salesperson-id mapping needs approval.
- Existing generic Orders pages currently allow broader department read access. Tracker scopes all its own paths; changing the legacy Orders/export authorization is a separate compatibility change and remains a privacy follow-up.

## AI and resource plan

Existing provider: OpenAI `AsyncOpenAI`, Responses API, `services/openai_client.py`, `OPENAI_API_KEY` and `OPENAI_MODEL`. Reuse that client with an isolated read-only tool registry; never use the operational agent's write tools. Per-request conversation only, provider `store=False`, 6 tool calls total, 1,200 output tokens per turn, 30-second overall timeout, 20 questions / 10 min / user. No live AI evaluation of customer records.

Current process RSS has not been measured in this audit. Task reports 270–420 MB in a 512 MB instance (92–242 MB nominal headroom before new request peaks). Fetch `/health` during deployment for an actual sample; do not equate a sample with worst-case headroom.

Initial cap targets: trip/issue projections 2 MiB serialized total with 24-hour TTL and 512 entries; historical projection cache 1 MiB total / 5 min; rate-limit and feedback identifiers at most 1,000 users / answers with expiry. Do not retain copied Zoho order caches or LLM conversation history. Serialized caps are not a Python RSS guarantee; document conservative overhead and bounded request concurrency after implementation. New Zoho cache size/cost is zero while disabled.

## Proposals awaiting approval

1. **Receiver and rejected quantities:** use existing Admin > Settings > Driver app forms. Add optional text `receiver_name` (Received by) and `receiver_position` (Position). For Partial/Failed add optional text `rejected_items` (JSON array of `{sku, quantity, unit}`) with conditional visibility. Current editable field types do not provide a repeating per-item quantity editor: structured JSON is a minimal interim option requiring crew training; a dedicated validated repeating UI is the better follow-up. No live template edits in this task. Existing answers can be read without a schema change.
2. **Permits:** proposed `delivery_documents` metadata: id, owner_type (customer/vehicle/trip/SO), owner_id, document_type, storage reference, expiry, uploaded_by/at. Logistics uploads; customer permits belong to customer, truck papers to vehicle, consignment documents to SO/trip. Define required document types and review authority first. This table and its read/write paths require approval; no migration now.
3. **Rules:** prefer existing `client_delivery_constraints` plus notes, avoiding a second table. If Zoho is the master, use contact custom fields published through a bounded periodic cache, with daily call measurement. No new customer contact calls now.
4. **Loading:** improve the existing manifest checklist and publish its confirmed evidence to current-day memory. Do not claim an unchecked or absent checklist is a pass. No new loader write step or schema now.
5. **Question log:** proposed table `order_tracker_questions`: id, user id, asked_at, question (bounded), tool names, duration, missing-data flags, feedback. Retention proposal 30 days. No tool payloads, credentials, phones or copied customer records. Until approved, structured app logs only; feedback logs only.
6. **Proactive updates:** proposal only: trigger scoped salesperson email or Cliq messages at delivered / partial / failed event, deduplicate by event id and channel, link to Order card, no live GPS or private crew data in notification. Needs recipient mapping, consent and delivery audit design. No n8n lead-generation workflow changes.
7. **Payment / PO reads:** do not enable a new provider-read path until daily volume and invoice linkage are measured. A 15-minute cache can exceed 200/day with only a few active orders. Cache-only answers are safer for this release. A bounded scheduled invoice-list batch may cover most cases cheaply, but pagination and payment-reference completeness must be verified before approval.
